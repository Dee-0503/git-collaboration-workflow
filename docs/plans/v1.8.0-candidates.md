# v1.8.0 Candidate Features

Collected during v1.7.0 development. To be evaluated before v1.8.0 planning.

## 审查架构根因分析：v1.7.0 PR #4 审查循环 20+ 轮不收敛

v1.7.0 PR #4 经历了 20+ 轮云端代码审查仍未收敛，暴露了当前审查 Agent 架构的 **5 个结构性缺陷**。
以下根因分析为候选特性 #1–#6 的设计提供共同的问题基线。

### 根因 1：无状态设计 — 每轮全新 LLM 调用，无记忆

审查 GitHub Action 每次触发时启动全新的 LLM 实例，没有任何跨轮次的状态持久化。
这意味着审查器无法"记住"上一轮已确认修复的 finding，也无法区分"新发现"和"已解决再提"。
→ 直接导致已修复 finding 被重复报告，是审查循环不收敛的核心原因之一。
→ 相关候选特性：**#4**（Finding 状态追踪）、**#6**（Agent 状态持久化）

### 根因 2：5 个并行 Agent 缺乏一致性协调

云端审查 Action 启动 5 个并行 Agent（每个审查不同文件集），但它们之间没有：
- **结果去重机制**：同一问题（如跨文件的公共函数签名变更）可能被多个 Agent 重复报告
- **一致性仲裁**：Agent A 认为某实现正确，Agent B 认为相同实现有 bug，无仲裁机制
- **共享上下文**：Agent 之间不共享中间结论，导致碎片化的、有时矛盾的审查意见

→ 直接导致 finding 数量膨胀和修复方向冲突。
→ 相关候选特性：**#4**（需增加去重与一致性检查）

### 根因 3：单向信息流 — 审查器看不到开发者回复

审查工作流只收集 `claude[bot]` 发表的内联评论（`/pulls/$PR/comments`），
不收集开发者的反驳回复。当开发者解释某个"问题"实际上是正确行为时，
审查器在下一轮看不到这个解释，继续报告相同的误报。

→ v1.7.0 中 finding 49（sed BRE 正则误判）连续 3 轮重复即为此问题的典型表现。
→ 相关候选特性：**#1**（双向审查对话）

### 根因 4：上下文 O(n) 累积导致 LLM "迷失"

每轮审查将**所有**历史内联评论注入 prompt。经过 20+ 轮，累积 60+ 条 finding 占据大量 token，
导致 LLM 注意力分散：
- 关键的新问题被海量旧 finding 淹没
- LLM 开始产生低质量、重复性的 finding
- 审查时间从 5 分钟膨胀至 60 分钟，最终超时

→ 相关候选特性：**#4**（已解决 Finding 跳过，缩减 prompt 体积 70%）

### 根因 5：修复递归 — 每轮修复引入新代码新 finding

review-watcher 自动修复 code-level issue 时，新代码本身成为审查目标。
审查器对新代码产生新 finding → 再修复 → 再产生新 finding，形成无限递归。
在无状态 + 无去重的架构下，这个递归没有收敛条件。

→ 相关候选特性：**#4**（回归防护）、**#6**（状态持久化提供收敛判据）

### 候选特性覆盖矩阵

| 根因 | #1 双向对话 | #4 Finding 跳过 | #5 APPROVE 能力 | #6 状态持久化 |
|------|:---------:|:-------------:|:--------------:|:-----------:|
| 无状态设计 | | ✓ | | ✓ |
| 并行 Agent 不协调 | | ✓ | | |
| 单向信息流 | ✓ | | | |
| 上下文 O(n) 累积 | | ✓ | | ✓ |
| 修复递归 | | ✓ | | ✓ |

> **结论**：5 个根因中有 4 个需要 #4（Finding 状态追踪）参与解决，#4 和 #6 深度耦合。
> 建议将 #1 + #4 + #6 作为 v1.8.0 的核心改进包合并设计与实施。

## 1. Inline Review Comment Reply — Bidirectional Review Conversation

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 cloud review workflow — 审查循环无法收敛的根因分析
**Priority**: High（直接影响审查收敛速度）

### Problem

当前审查工作流是**单向的**：审查器发表内联评论 → 开发者改代码 → 审查器看代码变更。
审查器**看不到**开发者在 PR 讨论区发表的反驳/解释，因为工作流只收集
`/pulls/$PR/comments`（内联评论）中 `claude[bot]` 发表的评论。

这导致两个问题：
1. **误报死循环**：审查器误判（如 sed BRE 正则），开发者反驳，审查器看不到反驳，
   下轮重复误判——v1.7.0 中 finding 49 连续 3 轮重复就是此问题
2. **修复后无确认**：review-watcher 修复了 code-level issue 后，原内联评论仍显示
   为未解决状态，人类浏览 PR 时难以区分已修复 vs 未修复

### Proposed Solution

#### 1.1 本地代理回复内联评论（像人类一样参与代码审查对话）

本地代理（review-watcher 或用户通过 /check-review）对审查发现做出回复：

**Code-level（已修复）**：
```bash
gh api repos/{owner}/{repo}/pulls/{pr}/comments/{comment_id}/replies \
  -f body="Fixed in commit abc123. Changed X to Y."
```

**Disputed（误报/争议）**：
```bash
gh api repos/{owner}/{repo}/pulls/{pr}/comments/{comment_id}/replies \
  -f body="Disputed: [evidence]. Verified via [method]. See commit history."
```

**Logic-level（需人工决策）**：
```bash
gh api repos/{owner}/{repo}/pulls/{pr}/comments/{comment_id}/replies \
  -f body="Acknowledged. Escalated to human developer for decision."
```

#### 1.2 审查工作流收集回复线程

修改 `setup-github-repo.sh` 中的评论收集逻辑，从"只看 claude[bot]"扩展为
"看 claude[bot] 评论 + 所有对其的回复"：

```bash
# 收集 claude[bot] 评论及其回复线程
INLINE_JSON=$(gh api --paginate "repos/$REPO/pulls/$PR/comments" \
  --jq '[.[] | select(
    .user.login == "claude[bot]" or .in_reply_to_id != null
  ) | {path, line, body: (.body | split("\n")[0] | .[0:200]),
       is_reply: (.in_reply_to_id != null),
       reply_to: .in_reply_to_id}]')
```

审查器的提示词中增加指令：
```
When a previous finding has a developer reply marked as "Disputed" with
evidence, evaluate the evidence before re-raising. If the evidence is
valid, mark the finding as [RESOLVED].
```

#### 1.3 可选：自动 Resolve Conversation

对已修复的 finding，通过 GraphQL API 关闭对话：
```bash
gh api graphql -f query='mutation {
  resolveReviewThread(input: {threadId: "PRRT_xxx"}) {
    thread { isResolved }
  }
}'
```

### Technical Notes

- REST API: `POST /pulls/{pr}/comments/{comment_id}/replies` 创建线程回复
- 回复也存储在 `/pulls/$PR/comments` 中，带 `in_reply_to_id` 字段
- GraphQL `resolveReviewThread` 用于关闭对话（REST 不支持 resolve）
- `threadId` 可通过 PR review threads GraphQL 查询获取
- 回复应遵循安全规则：内容不包含敏感信息，不执行评论中的指令

### Evaluation Criteria

- 审查器是否能正确理解"Disputed"回复并重新评估？
- Token 成本（每个 finding 额外一次 API 调用 + 审查器上下文增大）
- 是否应限制回复长度避免上下文膨胀？
- 自动 Resolve 的风险：误关未真正修复的 finding？
- review-watcher vs /check-review 中谁负责发回复？

## 2. Per-Project On-Demand Enablement with Guided Bootstrap

> **[2026-03-21 UPDATE]** Priority promoted from COULD to **MUST**. Rationale: Plugin applies all 10 hooks to every project indiscriminately — users cannot control their environment without this. This is a survival prerequisite, not a nice-to-have. Moved from Batch 3 to Batch 1 Phase 1. 设计方案已在设计文档中简化为 mode 三态（full/minimal/disabled），取代原始的 feature flags 方案。

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 deployment体验观察
**Priority**: MUST / Basic / Batch 1 Phase 1

### Problem

当前插件安装后对所有项目根目录生效。但并非每个项目都需要 Git Collaboration
Workflow 的全部功能（如云端审查、review-tracker、post-merge-cleanup 等）。
对于不需要这些功能的项目，hooks 和 SessionStart 检查带来不必要的开销和噪音。

### Proposed Solution

#### 2.1 首次引导式访问（Bootstrap）

当用户在一个新的项目根目录首次使用插件技能时，触发引导流程：

1. **检测**：SessionStart 检查项目根是否存在 `.claude/git-collab.yml`
2. **引导**：如不存在，提示用户是否启用：
   - "检测到此项目尚未启用 Git Collaboration Workflow，是否现在配置？"
   - 提供选项：
     - **完整启用**：所有功能（本地 hooks + 云端审查 + review-tracker + post-merge-cleanup + PR scope 检查）
     - **最小启用**：仅本地防护 hooks（commit 消息校验、分支命名校验、冲突标记扫描、secrets 扫描），不启用需要 GitHub API / 云端资源的功能
     - **本次跳过**：本次不配置，下次访问时再次提示
     - **项目禁用**：生成 `enabled: false` 配置文件，插件不加载任何功能，后续需手动编辑 `.claude/git-collab.yml` 修改
3. **生成配置**：根据选择生成 `.claude/git-collab.yml`，包含：
   ```yaml
   enabled: true
   features:
     cloud-review: true
     post-merge-cleanup: true
     review-tracker: true
     branch-validation: true
     commit-validation: true
     secret-scanning: true
   created_at: 2026-03-06T00:00:00Z
   ```

#### 2.2 持久化记忆

- 配置文件 `.claude/git-collab.yml` 纳入 git 管理（不在 .gitignore 中）
- 团队成员 clone 后自动继承项目配置，无需重复引导
- 后续 SessionStart 读取配置，按 features 开关决定加载哪些 hooks

#### 2.3 Hook 条件加载

```bash
# SessionStart hook 中：
if [ -f ".claude/git-collab.yml" ]; then
  ENABLED=$(python3 -c "import yaml; print(yaml.safe_load(open('.claude/git-collab.yml'))['enabled'])")
  if [ "$ENABLED" != "True" ]; then
    exit 0  # 插件已禁用，跳过所有检查
  fi
fi
```

各功能 hook 根据对应 feature flag 决定是否执行。

### Technical Notes

- 配置文件格式：YAML（与 Claude Code 生态一致）
- 路径约定：`.claude/git-collab.yml`（在 .claude/ 目录下，与 review-tracker.json 同级）
- 需要区分 "未初始化" vs "已禁用"：无文件 = 未初始化（触发引导）；`enabled: false` = 已禁用
- python3 `yaml` 模块可能不可用，考虑 fallback 到 grep/awk 简单解析
- `.claude/` 目录中 `review-tracker.json` 等运行时数据应在 .gitignore，但 `git-collab.yml` 配置不应忽略

### Evaluation Criteria

- 引导流程的用户体验是否自然（不打断工作流）？
- 配置文件是否应支持项目级覆盖（monorepo 场景）？
- YAML 依赖是否合理，还是应该用更简单的格式（如 JSON/INI）？
- 如何处理插件版本升级时的配置迁移？

## 3. PreToolUse Prompt Hook 性能优化：消除不必要的 LLM 调用

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 日常使用痛点 — 每条 Bash 命令触发 7 次 LLM 评估
**Priority**: High（直接影响日常体验）

### Problem

当前 7 个 PreToolUse hook 的 matcher 均为 `"Bash"`（hooks API 限制，不支持命令内容级匹配）。
每执行一条 Bash 命令（包括 `ls`、`echo` 等完全无关的命令），7 个 prompt hook 全部触发，
每个都需要一次 LLM 推理来判断"这是不是 git push？不是→allow"。

**实际开销**：
- 每条 Bash 命令：7 次 LLM 调用 + 4 次脚本执行（脚本 <5ms 可忽略）
- 日常开发中 Bash 命令占比最高，导致持续的延迟和 UI 提示噪音
- 4 个 command 脚本已有 grep 预检查，不相关命令 exit 0 无输出（已验证无 UI 噪音）
- **噪音全部来自 7 个 prompt hook 的 LLM 评估**

### Proposed Solution

#### 阶段一：3 个纯 prompt hook → command 脚本（消除 3 次 LLM 调用）

`prevent-direct-push`、`prevent-force-push`、`prevent-rebase-shared` 的判断逻辑
是纯确定性的，不需要 LLM：

| Hook | 当前（prompt） | 改造后（command 脚本） |
|------|---------------|----------------------|
| prevent-direct-push | LLM 判断是否 `git push` + 目标分支 | grep + 正则匹配，<5ms |
| prevent-force-push | LLM 判断是否含 `--force/-f` | grep `--force\|-f\|--force-with-lease`，<5ms |
| prevent-rebase-shared | LLM 判断当前分支 + rebase 命令 | `git rev-parse --abbrev-ref HEAD` + grep，<10ms |

**脚本行为**：
- 不相关命令（非 git push/rebase）：exit 0 无输出（UI 完全无感）
- 违规操作：exit 2 + JSON 错误消息（UI 显示拒绝理由）
- 推送到 integration 等软拦截：exit 0 + `{"systemMessage": "..."}` 警告

**注意**：command hook 不支持 `ask`（交互确认），仅支持 allow/deny。
推送 integration 的软拦截从 `ask`（用户确认）降级为 `systemMessage`（仅警告），
可接受因为 integration 推送在正常工作流中极少发生。

**效果**：每条 Bash 命令 **7 次 LLM → 4 次 LLM**

#### 阶段二（可选）：4 个 hybrid prompt 合并为 1 个统一 prompt

将 detect-conflict-markers、enforce-commit-format、enforce-branch-naming、detect-secrets
的 prompt 部分合并为 1 个 prompt，包含所有规则。

**效果**：每条 Bash 命令 **4 次 LLM → 1 次 LLM**
**风险**：prompt 变长（~2000 tokens），单点故障，难以独立维护

#### 阶段三（长期跟踪）：hooks API matcher 增强

等待 Claude Code hooks API 支持命令内容级匹配：
```json
"matcher": {"tool": "Bash", "contentPattern": "git push"}
```
彻底解决问题：每个 hook 仅在相关命令时触发，无需预检查或合并。

### Technical Notes

- 4 个现有 command 脚本已验证：不相关命令 exit 0 无输出，UI 无噪音
- command hook exit 码：0 = allow（静默），2 = deny（显示错误）
- command hook 不支持 `ask` 交互，仅 allow/deny + 可选 systemMessage
- 阶段一不影响 4 个 hybrid hook 的 command 脚本部分，仅替换 3 个纯 prompt hook
- 新脚本应复用现有脚本的模式：读 stdin JSON → 提取 command → grep 预检查 → exit 0

### Evaluation Criteria

- 阶段一投入小（3 个 ~30 行脚本）、收益大（-43% LLM 调用），应优先实施
- 阶段二的 prompt 合并是否会降低判断准确率？
- 推送 integration 的 `ask` → `systemMessage` 降级是否可接受？
- 是否应向 Claude Code 团队提交 hooks API matcher 增强的 feature request？

## 4. 审查收敛加速：已解决 Finding 跳过机制

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 审查循环 20+ 轮未收敛的实战痛点
**Priority**: Critical（直接决定审查是否能收敛）

### Problem

当前云端审查每轮都将**所有**之前的 claude[bot] 内联评论注入 LLM prompt 作为上下文。
随着审查轮次增加（v1.7.0 PR #4 经历 20+ 轮），累积评论量呈线性增长（60+ 条），导致：

1. **审查时间 O(n) 增长**：每轮 prompt 越来越大，5 个并行 Agent 各自处理巨大上下文
2. **审查器误判**：大量 STILL OPEN 旧 finding 淹没真正的新问题
3. **新增 finding 递归**：修复旧 bug 引入新代码，审查器对新代码产生新 finding，循环不收敛
4. **运行超时**：审查 Action 从最初 5 分钟膨胀到 60 分钟，最终被 GitHub Actions 超时取消

### Proposed Solution

#### 4.1 Finding 状态追踪

在审查工作流中引入 finding 状态概念：

| 状态 | 含义 | 后续轮次行为 |
|------|------|-------------|
| OPEN | 未修复 | 传入上下文，审查器重新评估 |
| RESOLVED | 已修复（代码变更确认） | **不传入上下文**，跳过 |
| DISPUTED | 开发者已反驳 | 传入上下文 + 开发者回复，审查器重新评估 |
| WONTFIX | 设计决策，不修复 | **不传入上下文**，跳过 |

#### 4.2 本地代理标记 Finding 状态

结合候选特性 #1（内联评论回复），本地代理通过 API 回复标记每个 finding：

- 修复后标记 `[RESOLVED] Fixed in commit abc123.`
- 争议标记 `[DISPUTED] This is BRE syntax, verified via xxd.`
- 设计决策标记 `[WONTFIX] Design decision: advisory boundary is sufficient.`

#### 4.3 审查工作流过滤已解决 Finding

修改 `prev-review` 步骤：只传入状态为 OPEN 或 DISPUTED 的 finding，
跳过 RESOLVED 和 WONTFIX，大幅缩减 prompt 体积。

#### 4.4 回归防护

已解决的 finding 跳过审查后，需要本地代理做回归守护：
- review-watcher 每轮修复后验证 RESOLVED finding 未被重新引入
- 如果已 RESOLVED 的代码行被再次修改，自动升级为 OPEN

#### 4.5 并行 Agent 结果去重与一致性检查

**问题**：5 个并行审查 Agent 各自独立运行，结果直接合并发布，缺乏去重和一致性仲裁（参见根因分析 #2）。这导致：
- 同一问题被多个 Agent 以不同措辞重复报告（如跨文件的函数签名变更被 2-3 个 Agent 分别提到）
- Agent 之间对同一实现产生矛盾判断，开发者无所适从
- Finding 数量虚高，干扰真正的优先级排序

**建议方案**：
- 在 5 个 Agent 完成审查后、发布评论前，增加一个**聚合去重阶段**
- 基于 file path + line range + issue category 进行语义去重
- 对矛盾 finding，由聚合器进行仲裁或标记为"需人工判断"
- 去重后的 finding 附带来源 Agent 标识，便于追踪

#### 4.6 Confidence Scoring 在大上下文下的准确率下降

**问题**：当前审查 Agent 对每个 finding 附带 confidence score（high/medium/low）。
但在大上下文场景下（20+ 轮累积 60+ 条历史 finding），confidence scoring 的准确率显著下降：
- LLM 对旧 finding 的重新评估倾向于保守（标记为 high confidence 避免遗漏），即使代码已修复
- 新 finding 的 confidence 被旧上下文稀释，真正的高优先级问题得不到突出
- 5 个并行 Agent 的 confidence 标准不统一，同类问题在不同 Agent 中获得不同 confidence

**建议方案**：
- 将 confidence scoring 与 finding 状态追踪（4.1）结合：仅对 OPEN 状态的 finding 进行 confidence 评估
- 引入**上下文窗口限制**：每个 Agent 的历史 finding 上下文不超过 N 条（如 10 条最近的 OPEN finding）
- 在去重阶段（4.5）统一校准 confidence score

### Evaluation Criteria

- 预期效果：60+ 条 finding 中约 70% 可标记为 RESOLVED，prompt 体积缩小 70%
- 审查时间预期从 60 分钟降至 10-15 分钟
- 回归防护是否足够可靠？标记错误的发现和纠正机制？
- 去重阶段的额外耗时是否可接受（预计 1-2 分钟）？
- Confidence scoring 校准的复杂度和维护成本？
- 与候选特性 #1 深度耦合，与 #6（状态持久化）联合设计效果更佳，建议 #1 + #4 + #6 合并实施

## 5. 审查器 APPROVE 能力：自动完成合并闭环

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 PR #4 合并死循环——branch protection 要求 APPROVE，但 claude[bot] 从未发出
**Priority**: High（缺失导致无法自动合并）

### Problem

main 分支保护规则要求 `required_reviews: 1` 且 `dismiss_stale: true`。
claude[bot] 的审查 Action 只提交 COMMENTED，从未发出 APPROVED。
每次推送新 commit，dismiss_stale 自动撤销之前的 approve，形成死循环。

### Proposed Solution

当本轮审查发现 0 个新 issue 且所有 OPEN finding 已 RESOLVED 时，
提交 `gh pr review --approve`，解锁合并按钮。

### Evaluation Criteria

- claude[bot] 误 approve 的风险？
- 是否需要额外人工审批作为安全网？

## 6. 审查 Agent 状态持久化：跨轮次记忆机制

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 审查循环 20+ 轮不收敛的根因分析——根因 #1（无状态设计）
**Priority**: Critical（与 #4 深度耦合，共同决定审查能否收敛）
**Dependencies**: 与 #4（Finding 状态追踪）联合设计，与 #1（双向对话）互补

### Problem

当前云端审查 GitHub Action 每次触发时启动全新的 LLM 实例，没有跨轮次状态持久化。
这意味着：

1. **无记忆**：审查器无法区分"首次发现"和"已确认修复后再提"，导致已修复 finding 被重复报告
2. **无一致性基线**：5 个并行 Agent 每轮各自独立判断，无法参考上一轮的共识结论
3. **无收敛判据**：审查工作流没有"所有 finding 已处理"的终止条件，只能靠轮次上限或超时中断
4. **调试困难**：20+ 轮审查后，无法追溯某个 finding 何时首次出现、何时被标记修复、何时又复发

### Proposed Solution

#### 6.1 Finding 状态映射持久化

在 GitHub Actions 的 artifact 或 PR label 中持久化 finding 状态映射：

```json
{
  "schema_version": "1.0",
  "pr_number": 4,
  "last_updated_round": 22,
  "findings": {
    "finding-001": {
      "file": "scripts/setup-github-repo.sh",
      "line_range": [142, 145],
      "category": "security",
      "summary": "sed BRE regex not validated",
      "status": "DISPUTED",
      "first_seen_round": 3,
      "last_evaluated_round": 22,
      "resolution_note": "BRE syntax is correct, verified via xxd"
    },
    "finding-002": {
      "file": "scripts/check-review.sh",
      "line_range": [80, 82],
      "category": "correctness",
      "summary": "Missing error handling for gh api call",
      "status": "RESOLVED",
      "first_seen_round": 5,
      "resolved_round": 8,
      "resolved_commit": "abc1234"
    }
  }
}
```

**存储方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| GitHub Actions Artifact | 原生支持，无外部依赖 | 90 天过期，跨 workflow 读取需额外步骤 |
| PR Label + Description | 可见性好，人类可直接查看 | 容量有限（label ≤ 50 字符），description 格式脆弱 |
| PR Comment（隐藏） | 容量无限，API 简单 | 需约定格式解析，评论列表变长 |
| 仓库文件（`.github/review-state/`） | 持久化最可靠，版本可追溯 | 每轮需 commit，增加 PR diff 噪音 |

**推荐**：GitHub Actions Artifact（主存储）+ PR Comment（人类可读摘要）双写。

#### 6.2 审查 Action 启动时加载状态

```yaml
# 审查 Action 中增加状态加载步骤
- name: Load previous review state
  uses: actions/download-artifact@v4
  with:
    name: review-state-pr-${{ github.event.pull_request.number }}
  continue-on-error: true  # 首轮无状态文件，允许失败

- name: Run review with state context
  run: |
    if [ -f review-state.json ]; then
      RESOLVED_COUNT=$(jq '[.findings[] | select(.status == "RESOLVED")] | length' review-state.json)
      echo "Skipping $RESOLVED_COUNT resolved findings from previous rounds"
      # 仅将 OPEN/DISPUTED finding 注入审查 prompt
    fi
```

#### 6.3 审查完成后更新并上传状态

```yaml
- name: Update review state
  run: |
    # 合并本轮新 finding 到状态文件
    python3 scripts/merge-review-state.py \
      --previous review-state.json \
      --current-round-findings new-findings.json \
      --output review-state.json

- name: Upload review state
  uses: actions/upload-artifact@v4
  with:
    name: review-state-pr-${{ github.event.pull_request.number }}
    path: review-state.json
    overwrite: true
```

#### 6.4 收敛判据与自动终止

基于持久化状态，定义审查收敛条件：

```
审查收敛 ≡ 本轮新 OPEN finding 数 == 0 AND 所有历史 OPEN finding 已处理
```

当收敛条件满足时：
1. 审查 Action 输出 `review_converged=true`
2. 触发 #5（APPROVE 能力）自动提交 approval
3. PR Comment 发布收敛摘要：总轮次、总 finding 数、解决率等

### Technical Notes

- Artifact 名称约定：`review-state-pr-{pr_number}`，每轮覆盖上传
- 状态文件 JSON schema 需版本化（`schema_version` 字段），便于后续扩展
- Finding ID 生成规则：`file_path + line_range + category` 的哈希，确保跨轮次可追踪
- 并行 Agent 结果合并时需先去重（参见 #4.5），再更新状态映射
- 首轮审查（无历史状态）应正常执行，状态文件从空开始构建
- 需处理代码大幅重构导致的 line range 漂移——使用 `git diff` 映射旧行号到新行号

### Evaluation Criteria

- Artifact 存储的 90 天过期是否影响长期 PR？（大多数 PR 应在此期限内关闭）
- 状态文件的大小限制？（预计单个 PR 不超过 100KB，远低于 Artifact 限制）
- 持久化增加的 CI 耗时？（上传/下载 artifact 通常 < 5 秒）
- 与 #4 的实施顺序：建议先实现 #4（内存中的 finding 状态追踪），再实现 #6（持久化到 artifact）
- 是否需要提供手动清除/重置状态的机制？（用于审查 Agent 判断错误时的人工干预）

## 7. 插件版本更新后引导式检测与验证

**Status**: Candidate (pending evaluation)
**Origin**: v1.7.0 → v1.7.0 插件更新体验——更新后"静悄悄"，无任何引导或确认
**Priority**: Medium（影响用户对更新是否生效的信心）

### Problem

当前插件通过 `/plugin marketplace update` + `/plugin update` 完成版本升级后，
用户没有任何反馈来确认：

1. **更新是否生效**：`installed_plugins.json` 是否已指向新版本缓存？
2. **新增组件是否完整**：新版本引入的 hooks、skills、agents、scripts 是否全部加载？
3. **什么变了**：用户不知道 v1.4.0 → v1.7.0 之间新增了哪些功能、修改了哪些行为
4. **是否需要额外配置**：新版本是否依赖新的外部工具、权限或 GitHub 配置？

现有 SessionStart hook (`check-repo-status.sh`) 只检查**仓库状态**（分支、保护规则等），
不检查**插件自身状态**（版本、组件完整性、changelog）。

### Proposed Solution

#### 7.1 版本变更检测

SessionStart 时检测插件版本是否发生变化：

```bash
# 在 check-repo-status.sh 或新脚本中
PLUGIN_VERSION=$(python3 -c "import json; print(json.load(open('${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json'))['version'])" 2>/dev/null || echo "unknown")
LAST_SEEN_VERSION=""
VERSION_MARKER="${REPO_ROOT:+${REPO_ROOT}/.claude/.plugin-version-seen}"

if [ -f "$VERSION_MARKER" ]; then
  LAST_SEEN_VERSION=$(cat "$VERSION_MARKER" 2>/dev/null || echo "")
fi

if [ "$PLUGIN_VERSION" != "$LAST_SEEN_VERSION" ] && [ "$PLUGIN_VERSION" != "unknown" ]; then
  # 版本变更detected，触发引导
  echo "$PLUGIN_VERSION" > "$VERSION_MARKER"
  # 输出 systemMessage 告知用户
fi
```

#### 7.2 更新后引导式验证

检测到版本变更后，输出结构化引导信息：

```
[Git Collaboration Workflow] Plugin updated: v1.4.0 → v1.7.0

What's new:
- /check-review skill: 查看云端代码审查结果
- review-watcher agent: 自动监控审查进度
- post-merge-cleanup hook: PR 合并后自动清理分支
- review-tracker: PR 审查状态追踪

Verification:
✅ 12 hooks loaded (7 PreToolUse + 2 PostToolUse + 1 SessionStart)
✅ 12 skills available
✅ 2 agents available
⚠️ /setup-repo recommended: GitHub Actions workflow may need update

Run /check-status for full health report.
```

#### 7.3 组件完整性校验

对比 `plugin.json` 中声明的组件与实际文件系统：

```bash
# 检查 skills 目录
EXPECTED_SKILLS=12
ACTUAL_SKILLS=$(find "${CLAUDE_PLUGIN_ROOT}/skills" -name "SKILL.md" -o -name "*.md" | wc -l)

# 检查 scripts 可执行权限
NON_EXEC=$(find "${CLAUDE_PLUGIN_ROOT}/scripts" -name "*.sh" ! -perm -u+x | wc -l)

# 检查 hooks.json 合法性
python3 -c "import json; json.load(open('${CLAUDE_PLUGIN_ROOT}/hooks/hooks.json'))" 2>/dev/null
```

#### 7.4 Changelog 展示

从 `CHANGELOG.md` 中提取当前版本的变更内容，精简展示：

```bash
# 提取两个版本之间的 changelog 段落
sed -n "/^## \\[${PLUGIN_VERSION}\\]/,/^## \\[/p" "${CLAUDE_PLUGIN_ROOT}/CHANGELOG.md" | head -20
```

#### 7.5 配置迁移提示

如新版本引入了新的配置项或依赖：

```
Migration notes:
- v1.7.0 requires: GitHub Actions workflow update for cloud review
- New config: .claude/review-tracker.json (auto-created on first use)
- Recommended: Run /setup-repo to verify GitHub settings
```

### Technical Notes

- 版本标记文件 `.claude/.plugin-version-seen` 存储在项目本地，不同项目独立追踪
- 标记文件应加入 `.gitignore`（每个用户各自的更新状态不应共享）
- 版本比较应使用 semver 语义：只在主版本号或次版本号变化时触发完整引导，
  patch 版本只显示简要通知
- 完整性校验应为 advisory（警告），不应阻塞会话启动
- Changelog 展示应限制行数（如 20 行），避免信息过载
- 与候选特性 #2（Per-Project Enablement）联动：
  引导流程中可提示用户更新 `.claude/git-collab.yml` 配置以启用新功能

### Evaluation Criteria

- 引导信息的详细程度：太少则用户仍困惑，太多则噪音大
- 首次 vs 后续：首次看到版本变更显示完整引导，后续会话仅显示"v1.7.0 active"
- 是否支持 `--quiet` 或配置项跳过引导？
- 多项目场景：同一个插件版本在 N 个项目中首次使用都会触发引导，是否可接受？
- 组件完整性校验的误报率？（如用户合法地删除了某个 skill）

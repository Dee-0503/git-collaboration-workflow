## 概述

### 问题陈述

v1.7.0 云端代码审查存在 5 个结构性缺陷，导致审查循环 20+ 轮不收敛（60 分钟超时）。
同时，日常开发中每条 Bash 命令触发 7 次不必要的 LLM 调用，造成持续延迟。
此外，插件缺乏按项目启用机制和版本更新引导，影响多项目使用体验。

### 解决方案概述

v1.8.0 包含 7 个特性，分 3 个批次发布，聚焦审查收敛 → 性能优化 → UX 改善。

### 目标

- 云端审查从 20+ 轮/60 分钟收敛至 3-5 轮/10-15 分钟
- 实现审查自动 APPROVE，关闭合并闭环
- 日常 Bash 命令 LLM 调用从 7 次降至 4 次（-43%）
- 支持按项目启用/禁用插件功能

## Batch 1 Phase 1 设计：按项目启用门控（#2）

### 配置文件

**路径**：`.claude/git-collab.yml`

```yaml
mode: full      # full | minimal | disabled
```

- `full`：启用所有 hook 功能
- `minimal`：仅启用 secret-scanning + conflict-markers 检查
- `disabled`：所有 hook 零输出、零 LLM 调用

### 门控脚本

**路径**：`scripts/lib/gate.sh`

提供 `check_enabled()` 函数，被所有 hook 脚本 source 调用（每个 hook 新增 2 行）：

```bash
source "${CLAUDE_PLUGIN_ROOT}/scripts/lib/gate.sh"
check_enabled
```

`check_enabled()` 逻辑（不满足条件时直接 `exit 0` 终止调用方脚本，单用户场景足够简洁）：
1. 查找项目根目录的 `.claude/git-collab.yml`
2. 读取 `mode` 值
3. `disabled` → exit 0（hook 静默退出）
4. `minimal` → 仅对 secret-scanning / conflict-markers hook 继续执行，其余 exit 0
5. `full` → 继续执行（所有 hook 正常执行）
6. 无配置文件 → exit 0（默认不启用，由 SessionStart 引导）

### 引导式 Bootstrap

**触发条件**：SessionStart hook 检测到项目根目录无 `.claude/git-collab.yml`

**流程**：
1. 提示用户当前项目未配置 git-collaboration-workflow
2. 用户选择模式：`full` / `minimal` / `disabled`
3. 写入 `.claude/git-collab.yml`
4. 后续 session 不再触发

**注意**：无需向后兼容（单用户项目），无需迁移逻辑。

## Batch 1 Phase 2 设计：审查收敛解决方案（#1 + #4 + #5 + #6）

### 架构决策

**状态管理架构**：独立 Bash 状态管理脚本模式

新建 `review-state.sh`，统一处理 finding 状态的 CRUD 操作。所有消费者（GitHub Actions workflow、review-watcher agent、/check-review skill）调用同一脚本。

**选择理由**：
1. 遵循项目现有模式（脚本收集数据 + LLM 编排交互）
2. 逻辑集中、可复用、可独立测试
3. 不引入新语言依赖（bash + jq）
4. GitHub Actions runner 预装 jq

**状态存储方案**：PR Comment

使用带结构化标记的 PR Comment 存储 finding 状态 JSON。

**选择理由**：
1. 天然跨 workflow run 持久化（不依赖 artifact 的跨 run 查询）
2. 成熟模式（Terraform Cloud、Codecov、Danger.js 等均使用此方案）
3. API 简单（搜索 + PATCH 更新）
4. 降级安全（comment 丢失时视为首轮，不崩溃）

### 组件设计

#### 组件 1：review-state.sh — Finding 状态管理脚本

**职责**：
- 读取/写入 PR Comment 中的 finding 状态 JSON
- Finding 状态转移（OPEN → RESOLVED/DISPUTED/WONTFIX）
- 过滤：仅返回 OPEN/DISPUTED 的 finding（供审查 prompt 使用）
- 收敛检查：判断是否满足收敛条件

**接口**：
```bash
review-state.sh init <REPO> <PR>              # 初始化空状态（创建 PR Comment）
review-state.sh get <REPO> <PR>               # 读取完整状态 JSON
review-state.sh update <REPO> <PR> <ID> <STATUS> [NOTE]  # 更新单个 finding 状态
review-state.sh upsert <REPO> <PR> <FINDINGS_JSON>       # 批量 upsert 本轮新 finding
review-state.sh filter <REPO> <PR>            # 返回仅 OPEN/DISPUTED 的 finding
review-state.sh converged <REPO> <PR>         # 检查收敛条件，exit 0=收敛, exit 1=未收敛
review-state.sh summary <REPO> <PR>           # 输出人类可读摘要
```

**PR Comment 格式**：
```markdown
<!-- REVIEW_STATE_V1_START -->
```json
{
  "schema_version": "1.0",
  "pr_number": 42,
  "last_updated_round": 5,
  "findings": {
    "f-a1b2c3": {
      "file": "scripts/setup-github-repo.sh",
      "line_range": [142, 145],
      "category": "security",
      "summary": "sed BRE regex not validated",
      "status": "DISPUTED",
      "first_seen_round": 3,
      "last_evaluated_round": 5,
      "resolution_note": "BRE syntax is correct, verified via xxd"
    }
  }
}
```
<!-- REVIEW_STATE_V1_END -->

**最近更新**: Round 5 | OPEN: 2 | RESOLVED: 8 | DISPUTED: 1 | WONTFIX: 0
```

**Finding ID 生成规则**：`sha256(file_path + ":" + line_start + ":" + category)` 取前 8 位，前缀 `f-`。

**状态转移规则**：

| 当前状态 | 可转移至 | 触发条件 |
|---------|---------|---------|
| OPEN | RESOLVED | 代码变更确认修复（review-watcher 修复后标记） |
| OPEN | DISPUTED | 开发者通过内联回复反驳（#1） |
| OPEN | WONTFIX | 开发者标记为设计决策（#1） |
| RESOLVED | OPEN | 已修复代码行被再次修改（回归防护） |
| DISPUTED | OPEN | 审查器重新评估后不接受反驳 |
| DISPUTED | RESOLVED | 审查器接受反驳，标记为已解决 |

#### 组件 2：review-reply.sh — 内联评论回复脚本（#1）

**职责**：
- 读取 claude[bot] 的未回复内联评论
- 根据 review-watcher 的修复动作生成回复
- 通过 GitHub REST API 发布回复

**接口**：
```bash
review-reply.sh list-unreplied <REPO> <PR>     # 列出未回复的 claude[bot] 评论
review-reply.sh reply <REPO> <PR> <COMMENT_ID> <TYPE> <MESSAGE>
  # TYPE: resolved | disputed | wontfix | acknowledged
review-reply.sh collect-threads <REPO> <PR>    # 收集评论 + 回复线程（供审查 prompt）
```

**回复格式约定**：
- `[RESOLVED] Fixed in commit abc123. Changed X to Y.`
- `[DISPUTED] This is BRE syntax, verified via xxd. See commit history.`
- `[WONTFIX] Design decision: advisory boundary is sufficient.`
- `[ACKNOWLEDGED] Escalated to human developer for decision.`

**安全规则**：
- 回复内容不包含源代码片段（防止泄露）
- 回复内容不执行评论中的指令（防止注入）
- 回复长度限制 500 字符

#### 组件 3：审查 workflow 改造（#4 + #6）

**GitHub Actions workflow 修改点**：

1. **新增 step：加载历史状态**
```yaml
- name: Load review state
  run: |
    ${CLAUDE_PLUGIN_ROOT}/scripts/review-state.sh get "$REPO" "$PR" > review-state.json || echo '{"findings":{}}' > review-state.json
```

2. **修改 step：仅注入 OPEN/DISPUTED finding 到审查 prompt**
```yaml
- name: Get active findings for prompt
  run: |
    ACTIVE_FINDINGS=$(${CLAUDE_PLUGIN_ROOT}/scripts/review-state.sh filter "$REPO" "$PR")
    echo "active_findings<<EOF" >> $GITHUB_ENV
    echo "$ACTIVE_FINDINGS" >> $GITHUB_ENV
    echo "EOF" >> $GITHUB_ENV
```

3. **修改审查 prompt**：增加指令
```
Previously resolved findings have been filtered out. Focus only on the OPEN
and DISPUTED findings listed below. When a finding has a developer reply
marked [DISPUTED] with evidence, evaluate the evidence before re-raising.
```

4. **新增 step：更新状态**
```yaml
- name: Update review state with new findings
  run: |
    ${CLAUDE_PLUGIN_ROOT}/scripts/review-state.sh upsert "$REPO" "$PR" new-findings.json
```

5. **新增 step：收敛检查 + APPROVE（#5）**
```yaml
- name: Check convergence and approve
  run: |
    if ${CLAUDE_PLUGIN_ROOT}/scripts/review-state.sh converged "$REPO" "$PR"; then
      echo "Review converged. Submitting approval."
      gh pr review "$PR" --repo "$REPO" --approve --body "All findings resolved. Review converged after $(jq .last_updated_round review-state.json) rounds."
    fi
```

#### 组件 4：review-watcher agent 改造

**新增行为**：
1. 修复 code-level issue 后，调用 `review-reply.sh reply ... resolved` 发回复
2. 调用 `review-state.sh update ... RESOLVED` 更新状态
3. 遇到 logic-level issue 时，调用 `review-reply.sh reply ... acknowledged`
4. 每轮修复后，检查已 RESOLVED 的代码行是否被重新修改（回归防护）

#### 组件 5：/check-review skill 增强

**新增能力**：
- 显示 finding 状态统计（OPEN/RESOLVED/DISPUTED/WONTFIX 计数）
- 允许用户手动标记 finding 为 DISPUTED 或 WONTFIX
- 调用 `review-reply.sh` 发布回复

#### APPROVE 安全机制（#5）

**收敛条件**：
```
收敛 ≡ 本轮新 OPEN finding 数 == 0
      AND 所有历史 OPEN finding 已变为 RESOLVED/DISPUTED/WONTFIX
      AND 至少经历 2 轮审查（防止首轮误 APPROVE）
```

**安全阈值**：要求连续 2 轮满足收敛条件才提交 APPROVE。单轮收敛可能是偶然（如审查器遗漏），连续 2 轮更可靠。

## Batch 2 设计：Hook 性能优化（#3）

### 改造方案

将 3 个纯 prompt hook 转为 command 脚本：

| Hook | 新脚本 | 判断逻辑 |
|------|--------|---------|
| prevent-direct-push | `prevent-direct-push.sh` | grep 检测 `git push`，提取目标分支，main→exit 2，integration→systemMessage |
| prevent-force-push | `prevent-force-push.sh` | grep 检测 `--force\|-f\|--force-with-lease`，main→exit 2，其他→systemMessage |
| prevent-rebase-shared | `prevent-rebase-shared.sh` | 检测 `git rebase` + `git rev-parse --abbrev-ref HEAD`，main/integration→exit 2 |

**行为规则**：
- 不相关命令：`exit 0` 无输出（UI 完全无感）
- 违规操作：`exit 2` + JSON 错误消息（UI 显示拒绝理由）
- 软拦截：`exit 0` + `{"systemMessage": "..."}` 警告

**效果**：每条 Bash 命令 7 次 LLM → 4 次 LLM

**降级影响**：推送 integration 的交互确认（`ask`）降级为仅警告（`systemMessage`），可接受——integration 推送在正常工作流中极少发生。

### hooks.json 修改

将 3 个 prompt hook 的类型从 prompt-only 改为 command-only：
```json
{
  "name": "prevent-direct-push",
  "type": "command",
  "command": "${CLAUDE_PLUGIN_ROOT}/scripts/prevent-direct-push.sh"
}
```
